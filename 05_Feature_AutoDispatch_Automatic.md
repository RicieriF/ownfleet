# Feature: Auto-Dispatch — Розумне призначення курʼєрів

> Статус: 📋 Запланована фіча
> Залежності: ETA/SLA feature (✅), self-assignment mode (✅)

---

## Що це і навіщо

Менеджер малого закладу витрачає десятки рішень на день на одне просте питання: "кому з курʼєрів дати це замовлення?". Ця фіча прибирає цей cognitive overhead — замінює ручний вибір або алгоритмічною рекомендацією, або повним авто-призначенням залежно від обраного режиму.

Побічний ефект: система збирає дані про реальну тривалість доставок і порівнює з розрахунковим ETA — що дозволяє виявляти аномалії в роботі курʼєрів і самокалібруватися з часом.

---

## Режими призначення

Поле `dispatch_mode` на `establishments` (enum, замінює `auto_dispatch boolean`):

| Режим | Хто призначає | Що бачить менеджер |
|-------|--------------|-------------------|
| `manual` | Менеджер вибирає вручну | Список курʼєрів без підказок (поточна поведінка) |
| `recommend` | Алгоритм рекомендує, менеджер підтверджує або змінює | Smart Assignment UI з виділеним рекомендованим курʼєром |
| `auto` | Алгоритм призначає автоматично | Повідомлення "Призначено: Іван (~2 хв до закладу)" з можливістю перепризначити |

**Важливо:** `recommend` і `auto` використовують **один і той самий алгоритм**. Різниця тільки в тому, хто натискає "підтвердити" — менеджер або система.

**Менеджер завжди вище системи** — в будь-якому режимі він може перепризначити або скасувати призначення.

**Self-select режим** (курʼєр сам бере з пулу) — **видаляється повністю**. Замінюється `recommend`/`auto`: менеджер зберігає контроль, курʼєр не мусить моніторити і "хапати" замовлення самостійно.

---

## Тригер призначення

**MVP (ця ітерація):** Менеджер натискає кнопку "Готово до відправки" на замовленні в дашборді. Саме в цей момент їжа готова і треба призначити курʼєра. Перед запуском алгоритму — **confirmation dialog**: "Їжа готова? Призначити курʼєра?" (захист від випадкового натискання, особливо критично для режиму `auto`).

**Майбутнє:** Poster/iiko webhook зі статусом "order_ready" → автоматичний тригер без участі менеджера. Вся логіка dispatch залишається незмінною — змінюється тільки джерело тригера.

```
├─────────────────────────────────────────────────┤
│ ✅ ПРИЗНАЧЕНО АВТОМАТИЧНО                        │

│  Іван Петренко                                   │

│  ETA до клієнта: ~18 хв                          │
│                                                  │

└─────────────────────────────────────────────────┘
```

При натисканні **[Перепризначити іншого]** — відкривається повний список доступних курʼєрів (той самий UI що в `recommend`). Менеджер обирає іншого → поточний курʼєр знімається, новий призначається.

### Конкурентне призначення (два менеджери одночасно)

Якщо два менеджери відкрили панель для одного замовлення і один встиг призначити раніше:
- Другий менеджер при спробі призначення отримує повідомлення: **"Це замовлення вже призначено Іванові іншим менеджером"**
- Якщо обидва обрали одного й того самого курʼєра — повідомлення не показується, замовлення вже призначено, все ок

### Що показується для кожного курʼєра:
- Тип транспорту + іконка
- Відстань до закладу / "В закладі" якщо < 150м
- Навантаження сьогодні: години + кількість доставок
- Розрахунковий ETA до клієнта (OSRM + transport_mode)
- Попередження якщо доставка нерозумна для цього типу транспорту

## Алгоритм вибору курʼєра

### Крок 1 — Формування пулу (фільтрація)

Курʼєр включається в пул якщо виконуються всі умови:
- На активній зміні (`shifts.ended_at IS NULL`)
- Немає активної доставки (`deliveries.status NOT IN ('assigned', 'in_progress')`)
- Останній GPS пінг < 5 хвилин тому
- В радіусі 1 км від закладу (PostGIS `ST_DWithin`)

### Крок 2 — Proximity tiers (пріоритет за зоною)

Система шукає курʼєра в найближчій зоні, розширюючись якщо порожньо. Максимальний радіус — 1 км: курʼєр за межею вже не є "поряд" незалежно від типу транспорту.

```
Зона 1: < 150м     → фактично в закладі, може виїхати одразу
Зона 2: 150м–1км   → поряд, ~3-8 хв до закладу
Fallback            → немає нікого в радіусі 1км → авто-retry (див. нижче)
```

Серед курʼєрів **однієї зони** застосовується workload_score.

### Крок 3 — Workload score (справедливість всередині зони)

```
workload_score =
  SUM(completed_at - started_at)   ← завершені доставки сьогодні (реальний час)
  + SUM(eta_seconds)               ← active/assigned доставки (не дати одному двічі при concurrent dispatch)
```

Курʼєр з **найменшим** `workload_score` в зоні отримує рекомендацію.

Тай-брейкер: менше доставок сьогодні → раніше почав зміну.

### Крок 4 — Транспортне попередження

Якщо відстань доставки перевищує розумний ліміт для типу транспорту:
- `walking`: > 2 км → ⚠ попередження в UI
- `bicycle`: > 8 км → ⚠ попередження
- `car` / `moto_gas` / `moto_electric`: без обмежень

Попередження НЕ блокує призначення — менеджер вирішує сам.

---

## Fallback: немає курʼєрів в радіусі 1км

Якщо пул порожній — **не Telegram, а авто-retry через Bull**:

1. Замовлення залишається в `pending`, `ready_at` зафіксовано
2. Bull ставить delayed job: "перевірити замовлення X через 1 хвилину"
3. Через хвилину алгоритм запускається знову — якщо курʼєр зʼявився, призначає автоматично
4. Якщо через `dispatch_no_courier_escalation_minutes` (дефолт: 10 хв) нікого досі немає → Telegram менеджеру як крайній ескалейшн

В дашборді замовлення, що чекає на курʼєра, позначається індикатором **"⏳ Очікує курʼєра"** — менеджер бачить що ситуація є і система активно шукає.

**Поведінка при знайденому курʼєрі після retry:**
- Режим `auto`: система призначає автоматично → WS event `dispatch:courier_found` → toast менеджеру "Знайдено курʼєра для замовлення #X, призначено: Іван"
- Режим `recommend`: WS event `dispatch:courier_found` → якщо панель відкрита — оновлюється з рекомендацією; якщо закрита — toast "Знайдено курʼєра для замовлення #X, підтвердіть призначення"

## Метрика ефективності курʼєра — "+N хв/дост"

Вимірює наскільки реальний час доставки (заклад → клієнт) відрізняється від розрахункового ETA.

**Важливо:** `eta_seconds` перераховується в момент виїзду курʼєра з закладу (`eta_started_at`) — тільки маршрут заклад→клієнт через OSRM. Це гарантує що обидва числа вимірюють одне й те саме. EtaModule вже детектує виїзд (>100м) — в цей самий момент він оновлює `eta_seconds` свіжим розрахунком. Це також покращує точність existing overdue alertів в RetentionModule.

```
actual_seconds = completed_at - eta_started_at    ← від виїзду з закладу
eta_seconds    = OSRM(заклад → клієнт)           ← перерахований при виїзді EtaModule

+N хв/дост = AVG(actual_seconds - eta_seconds) / 60   за сьогодні
             WHERE eta_started_at IS NOT NULL          ← доставки без фіксованого виїзду пропускаються
```

| Показник | Колір | Значення |
|----------|-------|---------|
| `< +15 хв` | 🟢 | Норма (підʼїзд, ліфт, клієнт відкриває двері) |
| `+15 до +30 хв` | 🟡 | Варто звернути увагу |
| `> +30 хв` систематично | 🔴 | Аномалія → Telegram alert менеджеру |

**Захист від хибних спрацювань:** флаг спрацьовує тільки якщо **3+ доставки підряд** або **середнє за день** перевищує поріг. Один затор — не аномалія.

Пороги налаштовуються в Settings закладу.

## Прозорість для курʼєрів (мобільний додаток)

На головному екрані в idle-стані курʼєр бачить **статистику всієї команди** за сьогодні:

```
Навантаження команди сьогодні

Іван     ████████░ 2г 20хв · 8 дост · +9 хв/дост  ✅  ← ти
Олег     ███████░░ 2г 05хв · 7 дост · +12 хв/дост ✅
Марина   █████░░░░ 1г 40хв · 6 дост · +8 хв/дост  ✅
```

- Прогрес-бари відносні (найбільший = 100% ширини)
- Власна стрічка виділена
- Метрика `+N хв/дост` видима всім
- Оновлюється разом із polling стану

**Ціль:** прозорість усуває конфлікти "мені дають більше роботи". Кожен курʼєр бачить що розподіл чесний.

## Самокалібрування системи

Якщо `+N хв/дост` систематично великий по **всіх тенантах і локаціях** — це сигнал що OSRM занижує ETA для українських реалій (дороги, трафік, піші ділянки).

Відповідь: глобальний `eta_buffer_factor` що множить OSRM результат перед збереженням в `eta_seconds`. Переглядається на основі агрегованих даних платформи.

## Зміни в БД

### Міграція `dispatch_mode`

```sql
CREATE TYPE dispatch_mode AS ENUM ('manual', 'recommend', 'auto');

ALTER TABLE establishments
  DROP COLUMN auto_dispatch,
  ADD COLUMN dispatch_mode dispatch_mode NOT NULL DEFAULT 'manual';
```

### Нова колонка `orders.ready_at`

```sql
ALTER TABLE orders
  ADD COLUMN ready_at TIMESTAMPTZ NULL;
```

`ready_at IS NOT NULL` — замовлення отримало тригер "їжа готова", алгоритм вже запущено (або в процесі retry). Використовується для idempotency `POST /ready` і відображення індикатора "⏳ Очікує курʼєра" в UI.

### Нові налаштування в `settings` JSONB

```json
{
  "dispatch_recommend_radius_km": 1,
  "dispatch_anomaly_threshold_minutes": 30,
  "dispatch_anomaly_min_deliveries": 3,
  "dispatch_no_courier_escalation_minutes": 10
}
```

## Нові API endpoints

```
POST /api/v1/orders/:id/ready
  → тригер "їжа готова", запускає алгоритм
  → idempotent: якщо ready_at вже встановлено — повертає поточний стан без повторного запуску
  → замовлення залишається в статусі 'pending' до фактичного призначення
  → повертає: рекомендований курʼєр + список доступних з workload/ETA
  → для 'auto': одразу призначає (status → 'assigned') і повертає результат
  → якщо пул порожній: ставить Bull retry job, повертає { waiting: true }

POST /api/v1/orders/:id/assign-recommended
  → менеджер підтверджує рекомендацію (режим 'recommend')
  → повторно перевіряє доступність курʼєра перед призначенням
  → якщо курʼєр вже зайнятий: повертає 409 + оновлений список доступних

POST /api/v1/orders/:id/reassign
  → body: { courierId: string }
  → викликає явний метод OrdersService.reassignDelivery(deliveryId, newCourierId)
  → delivery залишається в статусі 'assigned' — змінюється тільки courier_id
  → validates: delivery must be in 'assigned' state
  → WS event старому курʼєру: 'delivery:reassigned'
  → FCM push новому курʼєру
  → якщо delivery не в 'assigned': повертає 409 + { assignedTo: courierName }

GET /api/v1/couriers/workload-today
  → навантаження всіх курʼєрів закладу за сьогодні
  → доступний для ролей: manager, dispatcher, courier (multi-tenant guard)
  → використовується: Smart Assignment UI + мобільний stats
```

## Push-сповіщення курʼєру при призначенні

**MVP (обовʼязково):** При будь-якому призначенні через новий dispatch flow (recommend або auto) — FCM push курʼєру через існуючий `NotificationsModule`. Без push курʼєр дізнається про замовлення тільки при відкритті додатку — весь сенс авто-диспетчу губиться.

Перевірити що існуючий assignment flow в `OrdersModule` вже надсилає FCM push при `status → assigned`. Якщо ні — додати в рамках цієї фічі.

## Нові явні методи OrdersModule

```
OrdersService.runDispatchAlgorithm(orderId)   ← формування пулу + tiers + workload_score
OrdersService.assignCourier(orderId, courierId)  ← існуючий assign, використовується dispatch
OrdersService.reassignDelivery(deliveryId, newCourierId)
  ← validates delivery.status === 'assigned'
  ← оновлює delivery.courier_id (НЕ змінює status)
  ← WS event старому курʼєру + FCM push новому
  ← НЕ порушує state machine — статус не змінюється, операція через explicit method
```
